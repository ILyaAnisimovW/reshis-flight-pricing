# Аккаунты и границы защиты

## Реализованный контур

- Публичный расчёт доступен без входа; POST требует CSRF-токен.
- `/api/auth/me` и `/api/account/**` требуют серверной сессии. Скрытие HTML не является защитой API.
- Login принимает form-urlencoded, register — JSON. Регистрация не выполняет вход автоматически.
- Пароли хранятся как BCrypt-хеши, не открытым текстом. Максимум 72 UTF-8 байта связан с BCrypt.
- Cookie `JSESSIONID`: HttpOnly, SameSite=Lax; Secure включён в HTTPS-профиле. Тайм-аут сессии — 30 минут бездействия; перезапуск JVM сбрасывает сессии.
- SQL для поиска и создания пользователя параметризован. Уникальность логина обеспечена PRIMARY KEY.
- UI и API находятся на одном origin. JWT, сторонний OAuth и отдельный SPA-origin не используются.
- Секреты DB_URL/DB_USER/DB_PASSWORD передаются окружением Render; не помещать их в код, скриншоты, видео или браузерный JS.

## Данные

Таблица users: username VARCHAR(100) PRIMARY KEY, password VARCHAR(100) NOT NULL (BCrypt-хеш). Сессии не сохраняются в этой таблице. Постоянные пользователи — в Neon; локальный H2 не подходит для непостоянного диска Render.

## Риски и границы

Это учебный прототип. В опубликованном срезе c1a81820cb96 не заявляются MFA, email verification, сброс пароля, аудит действий, централизованное управление сессиями, прикладной rate limit или защита уровня WAF. Используйте вымышленные демонстрационные логины и отдельные пароли. Новые лимиты и requestId готовятся локально, но их нельзя считать свойствами уже опубликованного среза до проверки деплоя.

Нельзя гарантировать доступность при отказе бесплатных провайдеров или защиту от всех видов атак. Перед реальным использованием нужны отдельная оценка угроз, правила обработки персональных данных, мониторинг, резервное копирование и проверка восстановления.
